# 03 · 多 VPS 节点同步与配置生命周期（P1）

> 分类：【待验证】方案 + 【参考提炼】判据。

## 1. 同步拓扑

**面板是唯一事实源（source of truth），推模式，不让 VPS 各自拉取。**

```
FixCloud 主配置（NAS，0600）
   │  渲染 per-VPS 视图（只含该机 inbound + 路由）
   ├─ SSH(asyncssh) → 东京 VPS /etc/sing-box
   └─ SSH(asyncssh) → 香港 VPS /etc/sing-box
```

理由：拉模式会让每台机器持有订阅凭据、扩大泄露面；推模式凭据只留在面板。

## 2. 一致性判据【参考提炼】

| 判据 | 做法 |
|---|---|
| **version 单调** | 每次发布递增全局 version；节点侧记录已应用 version；低 version 拒绝应用 |
| **mtime 判重** | 内容 hash 相同则跳过写入与重载，避免无谓断连 |
| **原子写** | 写临时 → 回读校验 → `os.replace`；禁止就地覆盖 |
| **泄露断言** | 渲染后断言 per-VPS 视图不含其他机器的凭据、不含管理面字段、不含上游订阅 token |
| **check 不过整体回滚** | 任一台 `sing-box check` 失败 → **整批不发布**，不做"部分成功" |
| **漂移检测** | 定期回读节点侧配置 hash 与面板期望比对；不一致告警，不自动覆盖（先人工确认） |

## 3. 发布事务（建议 11 步，复用现有 save_service 思路）

1. 重读当前生产配置并记录 hash
2. 内存中结构化修改（不就地改文件）
3. 生成完整 Diff（人可读）
4. 语法与引用校验（官方 `sing-box check`）
5. 按策略备份（带时间戳，保留 N 份）
6. 写临时文件
7. 回读临时文件校验
8. 安全替换（原子）
9. 回读正式文件校验
10. 失败区分三态：**未替换 / 已恢复 / 需人工**
11. 写审计（不泄密）

> 我方现有 `save_service.py` 已实现 `unchanged / restored / recovery_failed` 三态，可直接复用该语义。

## 4. 重载与断连

- SIGHUP 成功会**重建实例 → 存量连接断**。因此：
  - 发布前判断是否真的需要重载（hash 相同则跳过）。
  - 批量发布**逐台滚动**，不要同时重载全部节点。
  - 重载后必须探活 + 客户端实测，不能只看进程活着。

## 5. VPS IP 变化后的配置更新

| 场景 | 处理 |
|---|---|
| VPS 换 IP | 面板侧更新节点 server 字段 → 重新渲染订阅 → 客户端自动更新 |
| DDNS 域名 | **不用 jpedge/hkedge 双栈域名做代理 server**（AAAA 指向家庭 NAS）；用 IPv4 或专用 A-only 子域 |
| 关联风险 | 参考项目教训：**换 IP 但复用旧域名+旧端口会被关联**，存活时间递减。换 IP 应同时换全新无关子域 + 独立证书 + 全新端口 + 白名单 + 静置（knowledge/10） |

## 6. 凭据与权限隔离

- 每台 VPS 用**独立 SSH 用户与密钥**，不复用 Lucky 隧道的 `lucky-tunnel`（权限不足且职责混淆）。
- 面板容器内密钥挂载只读、0600；不写进镜像层。
- 节点凭据按机器隔离；朋友版订阅只发线路 id。

## 7. 验收

- 两台同时发布：version 一致、hash 一致、无部分成功。
- 故意在其中一台写坏配置：整批拒绝，另一台不受影响。
- 故意让重载失败：自动恢复备份，探活通过。
- 漂移检测能发现手工改动并告警。
