# 多节点多协议架构（节点池分层 / 中转链式 / 出口选择 / 故障切换）

> 来源：JimmyChan233/homelab（私有仓库，经 Fork 授权学习）；本文件为脱敏后的设计思想提炼，非原文复制。
> 文中【已验证】= 本次审计实际读到的原作者记录；【推测】= 提炼者的推断。所有域名/IP/凭据均用文档示例值，真实值一律不出现。作者统称"原作者"。

## ① 通用可复用经验（可直接迁移）

### 1. 角色分离：一台机只干一件事
- 【已验证】代理节点跑"纯净系统 + 100% 专职代理"，用裸核 sing-box（不上面板），把内存/攻击面压到最低；算力/服务后端（监控门户、订阅中心、Docker、自动化）单独一台，**明确不拿来翻墙**（无对华优化、CPU 超售的廉价机只做后端）。住宅 IP 落地机、中转/入口机 likewise 独立角色。
- 收益：节点机 1GB 内存也能稳跑多协议；后端故障不影响代理；角色清晰让防火墙/监控/续费决策各自独立。
- 迁移要点：先画"角色表"（入口/代理/落地/后端/中转/哨兵），再给每台机定唯一主角色，避免"全能机"成为单点。

### 2. 异地双活 + 物理路径隔离
- 【已验证】主力（美西）+ 备份（欧洲）走**不同物理光缆**（太平洋海缆 vs 欧亚陆地光缆），单条海缆故障不会同时打死两台；客户端 fallback 自动测速容灾。
- 通用原则：容灾备份要隔离"故障域"——不仅地域不同，还要上游路由/海缆/供应商不同。同供应商同城两台不算容灾。

### 3. 节点池分层与"自动池准入门槛"
- 【已验证】分层：主力（大带宽 + 三网精品回程）→ 异地备份 → 区域备用（小配额/非优化回程，**仅手选不进自动池**）→ 商业机场兜底。
- 关键设计：**自动 fallback 池只放达标节点**。小配额（如 150GB/月）、回程绕第三国、延迟差的节点只作手选特殊用途（地区解锁/备用），不污染自动链。机场兜底池先"裁剪"——把慢节点踢出，池内全快则 url-test 按延迟选即最快，无需再跑带宽测速 cron。
- 每地内部再做协议级 fallback（REALITY→Hy2→Trojan），形成"地区×协议"二维容灾矩阵。

### 4. 链式代理 / 前后端分离（客户端零感知）
- 【已验证】客户端永远只连入口节点；入口节点服务端按域名分流：AI 域名 → 住宅落地出站，其余 → 本机直出。分流规则全在服务端，**订阅/客户端配置不用动**。
- 住宅落地入口只对入口节点 IP 开放（防火墙白名单 + 定时按 DDNS 自动同步，带"解析失败不动手"防锁死），不对公网暴露代理端口 → 更隐蔽。
- 通用原则：把"出口选择"下沉到服务端，客户端只认一个入口；新增/更换落地后端对客户端透明。

### 5. 中转与干净 IP 入口
- 【已验证】后端不直接吃公网，由中转机做"干净 IP 入口"：L4 socat 透传 80/443 → 后端 tailnet 地址，**TLS 证书仍留在后端**（中转不解密）。
- 中转腿优先走 tailnet：实测两台 VPS 间公网 TCP 间歇丢 SYN（双向约 60% connect 超时、ping 却正常），改走 tailnet 后稳定。【推测】公网跨机房路径质量不可假设，管理/中转腿用 overlay 网络兜底更稳。
- 同城中转延迟极低（同机房 leg2 ~2ms），适合游戏中转/低延迟业务；跨洲中转先逐对测路由（见③）。

### 6. 网站入口多机故障切换
- 【已验证】多台入口候选按线路优先级排成链（精品 HK > premium KL > 东京 BGP > 普通 HK），家里控制器每 2min 探测、自动改 DNS A 记录（灰云）把流量切到可达入口；入口机 socat → 后端 tailnet。
- 后端公网 80/443 封闭（DOCKER-USER 链 DROP + 删 ufw 放行），防止直连绕过入口层；ACME http-01 路径经入口仍可达。
- 通用原则：入口层与后端解耦，入口可多台热备，切换靠 DNS + 健康探测，后端只信 tailnet/入口来源。

### 7. 回家（远程访问家庭内网）架构
- 【已验证】规则把"目的=家庭网段"的流量交给回家组（IP-CIDR + no-resolve，置顶）。回家组用 fallback：[公网 DDNS 域名 1, 公网 DDNS 域名 2, tailnet 入口, DIRECT]，健康检查探家网关 HTTP、lazy:true、expected-status 200-599。
- 三个关键坑（均实测）：
  1. **DIRECT 必须排最后**：在二级路由网段对家网关的健康检查会"假阳"（报 alive/7ms 但真流量 502），排前会被误选。
  2. **CGNAT + NAT 发夹**：家宽经运营商 CGNAT、二级路由与主网关非对称 NAT → 在家连公网 IP 发夹不通；外部 VPS 测同隧道正常 → 纯家内拓扑问题，加 tailnet 入口绕开。
  3. **iOS 单 VPN 限制**：Stash 开则 Tailscale 关，tailnet 入口在 iOS 不可用；改用 Tailscale App + 路由器 advertise 子网路由，或直接走公网域名经反代（任何设备任何网络都通）。macOS/Android 上 Tailscale 与代理客户端可共存。
- 冷启动首包可能误用 DIRECT 约 5s 才切隧道（一次性）。

### 8. 出口选择按"内容 × 出口属性"匹配
- 【已验证】AI（尤其 Gemini）→ 住宅 IP 落地；普通流量 → 精品线路直出（更快）；流媒体 → 原生 IP / DNS 解锁机；IG 版权音频 → 按 **Meta 判定的国家归属**选出口（见⑩/03 文档，住宅 IP 未必判 US）。
- 健康检查要探"真实业务域名"而非通用连通性：AI 组探 api.openai.com/v1/models 且 expected-status:401（403=该出口被 OpenAI 封，判死）；通用 gstatic 探不到"AI 域名经住宅落地黑洞"。

### 9. 故障切换的稳定性设计（防翻转风暴）
- 【已验证】fail-open 降级：住宅落地挂 → AI 分流自动降级 direct（机房 IP 兜底，AI 仍能用），恢复自动切回。权衡：**可用性 > 出口纯度**。
- 三级落地：住宅(主) → 静态 ISP(备，不同供应商不同网络) → direct(机房兜底)，补上"住宅单点"缺的同级替代层。
- 切换走 sing-box selector + clash API **零重启**（优于"改配置+重启"式翻转，后者会掐断全体用户）。
- 探针必须 e2e（经本机入站→落地出站真拉业务域名，验 TCP+隧道+远端 DNS+出网），仅 TCP 探端口会漏掉"端口活但 DNS 死"的黑洞。
- **多次取样多数决 + 非对称迟滞 + 抖动锁**：单次采样在丢包链路上会误判，曾一天翻转 66 次=主力重启 66 次。改 3 次取样多数决、降级快(2轮)/升级粘滞(连续健康≥30min，每多抖一次门槛翻倍封顶 12h)、1h 内≥6 次翻转则锁定兜底。原则："不稳就别一直切，切到另一个 fallback 直接用"。

### 10. 换 IP 容灾与 DDNS 跟随
- 【已验证】利用供应商"每 14 天免费换 IP"（不重装、保留 key/配置/数据）作为抗封免死金牌；DDNS 定时自动跟随。换 IP 后清单：修复厂商塞回的无效网卡配置、更新落地机防火墙白名单、全舰队 fail2ban ignoreip、ssh config、文档；验证中国探针 TCP + 家里路由 flush DNS 后逐协议测。
- 坑：mihomo 上游 DoH 缓存旧 IP，第一次 flush 仍旧，隔几分钟再 flush。
- 进阶：换 IP 同步轮换**全新子域 + 新端口 + 新证书**，静置观察后再切回流量（避免旧域名/端口被关联封锁）。

### 11. 监控拓扑与噪音预算
- 【已验证】互监 + **外部哨兵**（在舰队之外盯后端，补"谁监控监控者"盲区）；已知公网路由黑洞对从互监 PEERS 移除避免每日误报；tailnet 作管理兜底。
- 通知噪音预算：批量维护静默执行、不新增告警通道，播报并入现有心跳/日报。
- 教训：机器活着 ≠ 服务活着，要做服务级黑盒验证（订阅拉取/协议握手/入口登录）。

- 【已验证】具体供应商组合：搬瓦工 LA（CN2 GIA/10099/CMIN2 三网回程、2TB/月、免费换 IP）主力；AkkoCloud 伦敦（1核1G/500GB）备份；LisaHost 西雅图住宅 VDS（真住宅 ASN）AI 落地；Contabo 东京（6核12G、超售、无对华优化）后端；VMISS 东京（500M/800GB）JP 出口/入口；Evoxt HK/MY（512MB 小机）备用；LisaHost HK 精品（CMI/CU2/CN2、50M/600GB月）。这些角色分配**强依赖各自套餐/线路/配额/价格**，换供应商需重测。
- 【已验证】家宽拓扑：运营商 CGNAT + 二级路由（192.0.2.0/24 示例段）+ OpenWrt 主网关（家网段 198.51.100.0/24 示例）；回家发夹问题由此拓扑产生，换网络环境结论会变。

- 【推测】"精品线优先于 BGP 地理线"的结论基于其电信家宽实测；不同运营商/地区需重测（见③）。

## ③ 需要重新验证的结论（含验证方法）
- 线路晚高峰加密吞吐：【已验证方法】必须测**加密 SSH** 吞吐（ssh 节点 "head -c 200M /dev/zero" 计时），不能测明文 HTTP（晚高峰 DPI 限明文会造假崩盘）；判据峰值加密吞吐守住≈基线且 ping<80ms 则留，加密也崩<5Mbps 则退；深夜数据不算。迁移到新线路须重跑。
- VPS 间公网可达性/路由：逐对 mtr + nexttrace 看最后一跳；ICMP 丢包≠TCP 丢包（曾"7-30% 丢包"复测为 ICMP 限速伪象，TCP 20/20 全通）。
- 住宅 IP 的 AI 通过率：脚本只测 ChatGPT，Gemini 须实际使用验货（账号历史也影响）。
- Meta 国家归属：curl -s4 https://<IP_GEO_API>/data/shared_data/ 取 country_code，逐出口测 3 次，**不能按地理位置猜**（伦敦 IP 可能属 HK ASN 被判 CN）。
- DERP 健康：要看客户端到 DERP 的 **TCP 可达性**而非仅 STUN（UDP）；IP 被墙 TCP 但 STUN 仍通时，设备照样选它当 home DERP → 打洞失败连接全超时。
- 某入口域名是否只放行特定地区来源：四地探针实测（曾某机场入口只放行大陆来源，在港全红）。

## ④ 可迁移到 FixCloud / Lucky / QNAP NAS 的具体做法
- **FixCloud（自建服务/面板侧）**：采用角色分离 + 裸核 sing-box 多 inbound；入口层多机热备 + DNS 健康切换（借鉴 entry-failover 思路）；后端公网 80/443 封闭、只信入口/tailnet；docker 防火墙规则用 PartOf=docker.service 幂等重放，防 daemon 重启后端口裸奔（P0 复发通道）。
- **Lucky（OpenWrt 反代/DDNS）**：回家/远程访问优先用 Lucky 公网域名反代（任何设备任何网络通，绕开 iOS 单 VPN 与 CGNAT 发夹）；DDNS 自动跟随换 IP；Lucky 做入口 TLS 终结，后端经 tailnet。健康探测改 DNS 的控制器逻辑可借鉴。
- **QNAP NAS**：不直接对公网暴露代理/管理端口，经 tailnet 或入口机访问；注意 QTS 权限墙（守护进程跑 admin/root，普通 admin 组 SSH 用户杀不了进程/写不了 qpkg.conf，sudo 要密码）→ 批量停用套件走 QTS UI 手点清单；监控 swap RAID 降级（mdadm 状态）与网卡 link flap（曾精确 48h 周期重协商，查交换机侧）；**别用 SMB-TimeMachine-to-QNAP**（已证脆弱，APFS 对象表清零零可恢复）；配置级备份 rsync over SSH 到另一台 NAS，成功静默 + 首跑核验落盘；清理前确认活依赖（如 /Photos 被归档任务每日写）。
